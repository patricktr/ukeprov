Wiggle Room — Build Roadmap

A ukulele improv trainer, built from ukulele-improv-prd.md. The gap it closes has three parts — not knowing where the notes inside a chord live, not knowing the one-finger variations that add motion without leaving the shape, and having nothing to play against. Every item below names the PRD section it comes from, what was actually measured rather than assumed, and the order to fix it in when it fails.

How to run this list

  • The sentence under the wiggle is the product. The fret shapes could be generated by anyone with a calculator. "Lift the pinky. Suddenly it's airy." could not. When an item trades dataset breadth against note quality, quality wins.
  • Chord tones are the skill; scales are the filler. Anything that makes the scale overlay compete with the chord tones for attention is a regression, however nice it looks.
  • Measure it, don't assert it. Every number in this document came out of a tool. Where something is unverified it says so, and the item stays open.
  • The avoid-list is load-bearing. PRD §5.5: "the feature that keeps me actually using the thing instead of hitting a wall on preset #3." A change that quietly makes an avoided chord reachable is a bug, not a convenience.
  • Ship-blockers vs. day-two. P0 items are what the PRD marks as such in §5. Everything else can land later without the tool being less useful than what preceded it.

What already exists, and why it isn't enough

PRD §1: "Every existing tool solves one of these in isolation… None of them connect the chord I'm playing to the notes I should aim for to the loop I'm playing over." Worth keeping visible, because every one of these is better at its own single job than this is — the whole bet is on the join.

The checklist

Phases 1–3 follow PRD §9. Phase 4 is the §10 open questions. Phase 5 is everything found while building that the PRD could not have known about, and Phase 6 is getting it online.

1 · The reference

Fretboard, chord tones, wiggles, avoid-list — PRD §9 Phase 1
  • Shipped. SVG in src/components/Fretboard.tsx, drawn entirely from the tuning plus fret arithmetic — no hardcoded positions anywhere, per PRD §7. Fret spacing follows real scale-length maths rather than being evenly divided: the distance from nut to fret n is L(1 − 2^(−n/12)). Seven frets is a third of the scale, so the taper is visible. An evenly-divided board looks wrong to anyone who has held the instrument, and it costs one line of arithmetic to be right. Strings run GCEA top to bottom, matching fret-string notation — so 0003 reads straight down the board and the mini diagrams in the wiggle cards use the same order. Tool: the app itself at pnpm dev; screenshot rather than trusting the DOM.
  • Shipped. R / 3 / ♭3 / 5 / ♭7 / 7 as text on the dot, with note names behind a toggle. Root is 18px and brightest, the 3rd 17px, the 5th 14px and recessive, the 7th 15.5px in a distinct hue — the hierarchy PRD §5.1 asks for, expressed in size as well as colour. Colour is never the only channel. Every dot carries its interval as text, so the board reads correctly in greyscale and for any colour vision. That is what makes the palette a legitimate choice rather than a risk — see the colour key above for the measured ratios.
  • Shipped. The parent scale is derived from the chord quality rather than the key — major for a major triad, mixolydian for a dominant 7, dorian for a minor 7, locrian for a diminished. So the ghosts describe the chord you are actually on, not the key you nominally started in. Ghosts hide entirely when an interval is isolated. "Show me only the 3rds" means only the 3rds; leaving the scale up underneath defeats the drill.
  • Shipped, and it revealed that the PRD is half-wrong about this — see 5.2. Default high-G, as specified. Everything downstream of the tuning recomputes: playback pitch, the open-string register line, the string gauges drawn on the board, and the "lowest note" readout under each shape. The 4th string is drawn fatter in low-G (3.6px vs 2.1px), because it is a wound string there and a thin reentrant one in high-G. That makes the toggle legible at a glance rather than being a setting you have to remember you changed. Verified: toggling in the browser moves the open-string line from G4 C4 E4 A4 to G3 C4 E4 A4, and the chord-tone dot count stays at 9 — which is the finding in 5.2.
  • Shipped, with one deliberate asymmetry. Tapping always plays — a pointer-down is a user gesture, so it can open the AudioContext. Hovering only plays once audio is already running, because browsers will not start an AudioContext on hover and a dot that sometimes makes noise is worse than one that reliably doesn't. Re-entering the same dot inside 140ms is ignored, so a jittery mouse doesn't retrigger. Sweeping across the board deliberately arpeggiates, which is the behaviour §5.1 describes. Keyboard reaches them too: chord-tone dots are focusable and play on Enter or Space. Ghost dots are not in the tab order — roughly fifty extra tab stops to reach scale context would make the board unusable with a keyboard.
  • Shipped. Reads exactly as §5.2 asks: "C major: C E G — nine places in the first seven frets." The count is computed, and it changes with the tuning and the fret window rather than being a sentence someone typed once. Chord tones are derived from root + quality, never stored. The PRD's §7 sketch has a tones field; this drops it, for the same reason §7 itself gives for computing fret positions. Two copies of the same fact is just somewhere for them to disagree.
  • Shipped. One button per chord tone, each carrying its own count — "there are only two 3rds down here" is itself the useful fact, so it goes on the button rather than being something you work out by squinting. Verified in the browser: with "3" active, exactly the three 3rd dots sit at opacity 1 and the other six at 0.16, with every ghost hidden. Checked by reading the rendered attributes, because a screenshot at 55% scale could not have told them apart.
  • Shipped. §5.3 is explicit that this "should feel like flipping through a card deck, not reading a table", so: one card per wiggle, everything on its face, nothing behind a disclosure triangle. Notation, a mini diagram per position, the sentence, a play button. The moving finger is picked out in amber on each diagram — the string that changed from the previous step. That is the entire pedagogical content of a wiggle, and before it was highlighted you had to diff two diagrams by eye. Diagrams are vertical while the main board is horizontal, deliberately. They answer different questions: the board is "where does this note live on the neck", the diagram is "what does my hand do". Every chord chart ever printed uses the vertical form and fighting that would help nobody. Play is tempo-linked — one step per beat at the current BPM, floored at 450ms — so a wiggle browsed here feels like the thing you will play over the loop. Fixed after looking at it: a four-step wiggle overflowed its card by about nine pixels and wrapped the last diagram onto its own line. Diagram padding 12px → 9px and the gaps 6px → 4px; all four now sit in one row.
  • Shipped, with both branches of §5.5 working. E is on the list by default, as specified. Six chords are pre-suggested as genuinely awkward — E, B♭, Bm, F♯m, Bdim, Edim — and any of the 32 can be added. The rule: a vamp containing an avoided chord is shown with the substitution if one exists, and hidden entirely if not. Silently dropping a chord from a four-chord loop would be worse than either. The substitutions are musical, not cosmetic. Bdim → G7 and Edim → C7 both work because vii° is V7 without its root — the substitute contains every note of the chord it replaces. F♯m → A is the relative major. B♭ → B♭maj7 loses the half barre. E → E7 at 1202 is the PRD's own example. Verified end to end in the browser. Avoiding E turns the "Descent" preset into Am G F E7 ✦. Avoiding C — which has no substitute — hides 9 of the 17 vamps and surfaces the notice explaining why, leaving the 8 that use C7, Cmaj7 or no C at all.
  • Shipped at 32 chords against the §7 estimate of "roughly 25", covering all seven keys plus the vii° of each and the borrowed dominant that makes each minor key work. Hand-authored in src/data/chords.ts and meant to be edited — the shapes could be generated, the sentences could not. 192 assertions run on pnpm test. Every shape's pitch classes must be a subset of the chord's tones; every tone must be present unless the shape declares it omitted; declared omissions must genuinely be absent; nothing may reach past the 7th fret; no stretch may exceed four frets; and no wiggle step may move more than two strings — past that it is a chord change, not a wiggle. It has already earned its keep. Em 0402 was authored claiming to omit the 5th; the B on the 1st string is the 5th, so the claim was false. Caught on the first run, before it could teach anyone the wrong thing. Tool: pnpm test. Run it after editing the dataset — that is what it is for.
  • Shipped. Not in the PRD, but it is the join the PRD's problem statement asks for — "connect the chord I'm playing to the notes I should aim for". Selecting a voicing draws a white ring around exactly those dots, so the shape under your fingers and the target notes are visibly the same object rather than two diagrams that happen to be on the same screen.
2 · The loop

Vamp player, metronome, tempo, now/next — PRD §9 Phase 2
  • Shipped. §5.4 sets the bar at "good enough to play along with, not good enough to record", and Karplus-Strong clears it for about four lines of arithmetic: a burst of filtered noise through a delay line one period long, averaged with itself each time round. The two-point average is doing the work. 0.5 × (x[n−N] + x[n−N−1]) is a lowpass, so high harmonics decay faster than low ones — which is what a real string does, and why this sounds like nylon rather than like an oscillator. The excitation is lowpassed too. Raw white noise gives a harpsichord-ish zing; rolling the top off the initial burst is what makes it read as a ukulele. Buffers are rendered once per pitch and cached — about a millisecond for two seconds of audio, so a fast strum costs nothing after the first time through a shape. Strums stagger by 16ms per string, 4th to 1st for a down-strum, with each trailing string slightly quieter. Zero stagger is a chord stab, not a strum.
  • Shipped, as §8 insists: "Scheduling via a lookahead timer, not setTimeout per beat — timing drift will make the vamp unusable." Web Audio's clock schedules the sound to the sample; a 25ms timer only decides when to top the queue up, 200ms ahead. The lookahead window is a trade. Everything already queued keeps sounding after a tempo change or a stop, so 200ms is long enough to survive a stalled timer and short enough that pressing stop feels immediate. A starved timer re-anchors instead of catching up. A background tab clamps setInterval to once a second and a sleeping laptop stops it entirely; without a guard the fill loop would then queue every missed beat at a time already in the past, and Web Audio fires those instantly — a burst of clicks all at once. It now skips the missed beats and snaps back to the beat grid, so the loop stays in phase. Verified against the wall clock: sampling the chord display over 13 seconds at 90bpm gave chord changes every 2.63s against an expected 2.667s — inside the 500ms sampling granularity. See also 5.1, which is about the other half of this and was a real bug.
  • Shipped. Triangle-wave click at 1560Hz accented, 940Hz otherwise, with a 60ms exponential decay. The count-in accents every beat; once running, only the first beat of each chord is accented, so the click tells you where you are in the bar rather than just that time is passing. All three are independently switchable — click, chord strum, count-in. Playing against the strum teaches the harmony; playing against the click alone is harder and is the point after a few weeks.
  • Shipped at exactly the §5.4 range. Tempo and the sound toggles are pushed into the running scheduler rather than restarting it — you change tempo while playing, and a restart would drop you back into the count-in. Changing the chords themselves does restart, because there is no sensible place to land mid-loop.
  • Shipped. §5.4 calls NEXT "critically" important and it is right: the only reason to look up from the strings is to find out what is coming, and a chord you learn about on the beat it arrives is a chord you fluff. So NEXT carries the same weight as NOW, in amber — a colour that says prepare rather than play. Names are short — "Am", not "A minor". At arm's length from a music stand the short form reads instantly and the long one does not, and it is the form §6's own sketch uses. Derived from root plus quality suffix so it can't drift from the dataset. Beat dots below, with the downbeat wider. Fixed after looking at it: while stopped this panel was showing the loop's first chord at full weight while the fretboard showed whichever chord you had picked to browse — two different large chord names competing on one screen. It now dims to 55% when stopped and the caption reads "the loop, when you press play".
  • Shipped — 17, against §10's guess of "12–15 before it feels like a real library". Grouped by feel rather than by key, exactly as §10 asks: sunny, wistful, driving, old-time. Every one of the seven keys appears at least twice, and the I–vi–IV–V that §2 names as the success condition is the first item in the list. Two presets exist to exercise the avoid-list rather than to be played: "Descent" (Am G F E) is the reason E is on the list by default, and "Pop four" in D contains Bm.
  • Shipped — and it was very nearly missed. §5.4 reads "Pick a progression from a preset list, or build one from 2–4 chords." The preset half went in early and the builder did not, and nothing surfaced the gap until §5.4 was read back against the finished app rather than against the plan. Worth remembering: the plan said "vamp player", and the vamp player worked. The custom vamp is a Progression like any other, which is the whole trick. It carries a custom feel, slots into the same dropdown under "Yours", and travels the identical resolve path — so the avoid-list applies to it for free rather than needing a second implementation that could disagree with the first. "+ Build your own…" seeds from the key's tonic and dominant rather than starting empty. Two chords that already sound like a progression is a better place to begin editing than two blank slots. Adding a slot repeats the last chord, since you are about to change it anyway and a random pick would be a worse default than an obvious placeholder. Verified in the browser: seeds C G in the key of C, adds up to four and then hides the add button, persists to customChords across a reload, and setting the fourth slot to E — which is on the avoid-list — makes the dropdown read Your vamp · C G Am E7 ✦. Same substitution, same marker, same code path as a preset.
  • Shipped. Not in the PRD, but you are holding an instrument — reaching for a mouse to stop the loop means putting the uke down. Ignored while focus is in a control, so it never fights a dropdown or the tempo slider.
3 · The polish

Prompts, scale overlay, session memory, samples, iPad — PRD §9 Phase 3
  • Shipped. Fourteen constraints across three levels, including all five §5.6 names. The level selector exists so the button stops handing you "root and 3rd only" in month three — not so there is a score. Deliberately not gamified, per §5.6: "No streaks, no points." Nothing is persisted, nothing is counted, and pressing again discards the last one. The only state is which level you asked for, and that resets with the session.
  • Shipped: major, natural minor, both pentatonics, mixolydian, blues, plus the chord's own parent scale as the default. Kept secondary by construction, as §5.7 asks — "chord tones are the skill, scales are the filler". The overlay only ever changes which notes appear as ghosts; it can never restyle a chord tone or add a dot that competes with one. So there is no setting that makes the scale louder than the chord.
  • Shipped, taken literally. §5.8: "Remember last vamp, tempo, tuning, and avoid-list in localStorage. Nothing else persists." So the view toggles — note names, interval isolation, scale overlay, look-ahead — deliberately start fresh every session. They are things you reach for inside a session, not settings you hold an opinion about between them. Every read and write is wrapped. Private browsing and cleared site data both throw rather than returning empty, and the app has to work with no storage at all. If this turns out to be wrong in use — if losing the scale overlay every session is annoying rather than clarifying — it is a one-line move from the session object to the persisted one. Worth actually noticing over a week before changing it.
  • Open, and deliberately so. §5.4 calls this "a Phase 3 upgrade" and the synth "fine for v1". Use the synth for a few weeks first — if the loop is already good enough to play against, this is cost with no benefit. The real cost is not the code. Recording or licensing a clean multi-velocity strum set, then shipping it: even a modest set is several megabytes against the current ~87 KB gzipped, on a site whose whole appeal is that it opens instantly. Target: only worth starting if the synth is actually getting in the way. Decide by playing, not by listening to it in isolation. If it goes ahead, in order:
    1. One sample per open string, pitch-shifted per fret, before considering a full per-chord set.
    2. Lazy-load on first play so the reference half still opens instantly.
    3. Keep the synth as the fallback — it works offline and costs nothing.
  • Open. §3 is clear this is not the target — "Nice if it works on an iPad on a music stand, but desktop is the target" — so this is a genuine P2, not a disguised blocker. What is already true: the layout is a responsive grid that collapses to one column below 1024px, the fretboard scrolls horizontally rather than squashing below 760px, and every tap target is a real control. Nothing is desktop-only. What is unverified: whether 7 frets at iPad width are legible from across a room, whether the wiggle cards are readable at one column, and whether hover-to-play does anything sensible under touch. None of that can be answered from a desktop browser at a simulated width. Target: chord names readable at about two metres; no horizontal scrolling of the page itself; the loop controls reachable without leaning in. Tool: a real iPad on a real stand. A DevTools device emulation will not answer the legibility question, which is the only one that matters here.
4 · Open questions

The four things PRD §10 left undecided
  • Answered with a switch rather than a guess. §10: "Probably yes, but it might be visually noisy." Both halves of that are right, so "Look ahead one beat" is a toggle, default off. Having built it: it is genuinely a bit noisy. The whole board repaints on the last beat of every chord, which at 90bpm is every 2.7 seconds. Useful when you are learning a progression, distracting once you know it — which is exactly the kind of thing that should be a switch and not a decision made in a document. Decide it by using it for a week and seeing whether the toggle is ever on. If it never is, delete it.
  • Open, deferred exactly as §10 says — "Start at 7." Every shape in the dataset fits, including the up-the-neck voicings, and the test suite enforces that so it cannot quietly stop being true. The change is cheap when it comes. FRET_COUNT is one constant and the board geometry is computed from it; the scale-length maths already produces correct spacing at any fret count. The real work is the SVG getting narrower per fret, which is a legibility problem, not a maths one. Decide it by this test: when you find yourself wanting a note that is not on screen. Not before. Widening the board now would shrink every dot for a need nobody has felt yet.
  • Moot, and the §10 instinct was still right. The question was "is the diagram enough, and will the temptation to build audio early eat the whole project?" Since the build covered all three phases, the wiggles have audio. The instinct held anyway: the reference half was built first and works completely in silence. The AudioContext is created lazily on the first gesture, so nothing about the fretboard, chord tones or wiggle diagrams depends on audio existing. Had the project stopped at Phase 1, it would have been a complete tool.
  • Answered: 17, against the §10 guess of 12–15. Organised by feel, as §10 specifies. The count matters less than the coverage. Seventeen is enough that every key appears twice and each of the four feels has at least three, which is what stops the list reading as a handful of examples. Adding more is nearly free — one object in src/data/progressions.ts, and the test suite checks the chord ids exist and the length is 2–4.
5 · Found while building

Things the PRD could not have known, and one thing it got wrong
  • Fixed. The standard recipe for a Web Audio scheduler — the one §8 is describing — pairs a lookahead timer for sound with requestAnimationFrame for the visuals, so a chord is painted when you hear it rather than when it was queued. That is the right instinct and the wrong tool. Symptom: the NOW display sat about three seconds behind the audio. Pressing play and waiting four seconds showed "count in 3", a moment that should have passed at 1.45s. Cause, measured rather than guessed: a two-second probe counting both clocks returned rAF at 1.4 frames per second while setInterval held its full 40/sec, with document.visibilityState === "visible" and document.hasFocus() === true. rAF is throttled whenever the page is not painting normally — a background tab, a low-power display, an offscreen renderer — and it reports itself as perfectly healthy while doing so. Why it matters more here than in the recipe: §5.4 makes NEXT "critically" the point of the display. A chord display that silently falls seconds behind the audio is worse than no display at all, because you trust it. Fix: drain the beat queue on the scheduler's own 25ms timer. Beats are discrete events, so rAF's smoothness buys nothing — at the top tempo of 160bpm, 25ms is 6% of a beat and inaudible. Verified after the change: chord changes every 2.63s at 90bpm against an expected 2.667s, over a 13-second sample.
  • §5.1 says: "the same shape gives you a different lowest note and the chord tone map changes." The first half is right. The second is not. Why: G3 and G4 are the same pitch class. Every dot on the board is a pitch class, so the entire interval map — which fret is the root, which is the 3rd, how many places each has — is identical in both tunings. Confirmed in the browser: toggling tuning leaves the chord-tone dot count at 9 and every label unchanged. What actually changes is register, and that genuinely matters: in low-G the 4th string drops an octave, so the lowest sounding note of a shape is usually a different note. 0003 has C on the bottom in high-G and G on the bottom in low-G — the same chord, sitting on a different bass. So the toggle is real but the fretboard is the wrong place to look for it. Rather than let an unchanged dot map imply the switch did nothing, the app states the register directly — an open-string readout under the board (G4 C4 E4 A4 vs G3 C4 E4 A4), a "lowest note" line under each shape naming both the pitch and its interval, a fatter 4th string drawn in low-G, and a note in settings saying so in as many words.
  • Fixed, after computing the ratios instead of trusting the design. --color-dim was #626d7e — 3.66:1 on the page ground and 3.05:1 on a panel, both under the 4.5:1 AA floor. It is not decorative: it carries the fret numbers, the section headings, the open-string readout and the wiggle fret notation. Now #808d9f, at 5.69:1 and 4.74:1 — still visibly quieter than --color-muted above it, so the hierarchy survives. The ghost dots were #39414e at 1.64:1 on the board, which is close to invisible, and they are meaningful content — the scale context §5.1 asks for. Now #5e6a80 at 3.09:1, clearing the non-text threshold while staying 3× dimmer than a chord tone at 9.22:1, so they still cannot be mistaken for a target note. The interval colours all passed already — 9.81, 6.04, 7.06 and 6.60:1 for the dot labels. Listed in the colour key above so a future palette change has something to check against. Tool: WCAG relative-luminance maths, run over the actual token values. Takes a minute and catches what looking at it does not.
  • Fixed. When the avoid-list hid the vamp you were on, the app fell back to a playable one and wrote that back to the store. So avoiding a chord and then un-avoiding it left you stranded on the substitute, with your actual choice gone. Found by using it, not by reading it — toggling C on and off while testing §5.5 and noticing the vamp had silently become something else. Fix: progressionId stays your choice; the fallback is computed for display and playback only. Un-avoiding the chord brings your vamp straight back.
  • Caught by the test suite on its first run, which is the entire argument for having one. The two-finger Em voicing was authored as omitting the 5th, with a note reading "loses the B, keeps the mood". The B is on the open 1st string. It omits nothing. Why this class of error is worth machinery: it is invisible by inspection, it sounds fine, and it would have taught the wrong thing indefinitely. The assertion that declared omissions must genuinely be absent costs four lines and catches every future instance. Related, and kept: D7 2020 and B7 2320 really do omit their roots. They are marked omits: ["R"] and the app says so on screen, rather than quietly presenting a rootless voicing as the full chord.
  • Open. What is done is not the same as what is verified. Built in already: every interval carries a text label so colour is never the only channel; contrast measured and fixed (5.3); chord-tone dots are focusable with Enter/Space to play and carry labels like "C4, the 3rd of C major, string E fret 0"; the settings drawer is a real role="dialog" with Escape to close and focus moved into it; focus-visible outlines throughout; prefers-reduced-motion honoured. Not verified: a full keyboard traverse of the app, a VoiceOver run over the fretboard, and whether the SVG's per-dot labels are actually useful in sequence or just noise. Automated checks find roughly a third of accessibility problems; the rest needs ten minutes with the tools switched on. Target: reach and operate every control by keyboard alone; the fretboard comprehensible with the screen off. Tool: VoiceOver (⌘F5) and a Tab-key pass. Axe DevTools for the floor.
6 · Ship it

Vercel, the domain, and the first production deploy
  • Shipped: github.com/patricktr/ukeprov, public, default branch main.
  • Shipped. Project ukeprov under the Untitled Repo LLC scope, framework preset Vite, build pnpm build, output dist, install pnpm install, Node 24.x.
